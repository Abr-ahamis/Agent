# Bug bounty vulnerability class checklist

Run a check only when the asset, technique, accounts, and request volume are allowed by the current program rules. The listed signals are hypotheses. Use controlled accounts and fixtures, stop at minimum proof, redact all evidence, and never inspect unrelated user data.

| Class | What to look for / why | Tools and controlled test | Positive result vs false positive | Alternative / safe impact proof | Evidence and report |
|---|---|---|---|---|---|
| Authentication and session | Weak identity binding, session rotation/invalidation gaps, insecure cookie flags, auth bypass; could expose account functions. | Browser DevTools, proxy, `curl`; compare fresh/old sessions, logout, role changes, and controlled accounts. | Positive: protected action remains possible across a boundary that should be revoked. False positive: cached page, public content, or still-valid parallel session by design. | Test a harmless owned profile field or non-sensitive protected page; ask program for approved account fixtures. | Sanitized before/after request, session lifecycle, role, expected policy, and minimal impact. |
| Authorization / IDOR / function-level access | Object IDs, tenant boundaries, admin routes, GraphQL resolvers, bulk/export endpoints; server may trust caller-supplied object/role. | Burp repeater or `curl`; replay the same operation as two approved accounts, vary one object/function identifier at a time. | Positive: account A can read/change account B's controlled fixture or invoke a forbidden function. False positive: shared/public object, test fixture permission, or client-side display difference only. | Use two researcher-controlled accounts/records; demonstrate metadata or a harmless reversible test value only if rules allow. | Both identities/ownership, exact endpoint and field, redacted requests/responses, expected/actual boundary, no third-party data. |
| Input validation and injection: SQL/NoSQL, command, template, deserialization | Input reaches an interpreter/sink with unsafe construction; may alter query, execution, or object processing. | Source review, proxy/manual requests, approved scanner only if allowed; start with benign syntax/marker and compare control input. | Positive: reproducible server-side behavior tied to the input and sink. False positive: generic error, WAF response, client validation, timing noise, reflection, or scanner signature. | Verify with a harmless boolean/unique marker or source/config evidence; do not read tables, execute commands, or trigger side effects. | Exact parameter/content type, control and test response, reproducibility, sink evidence, tested impact, and limits. |
| XSS | Untrusted content reaches an executable browser context without context-appropriate encoding; can affect user sessions/actions. | Browser DevTools and proxy; use a benign, self-owned test page/account and inert marker before any approved proof. | Positive: controlled browser executes researcher-supplied script in the claimed origin/context. False positive: HTML-escaped reflection, text node, CSP-blocked payload, extension injection, or self-XSS outside threat model. | Prefer an inert DOM marker; do not target other users or exfiltrate data. Verify stored/reflected context and required victim interaction. | Sanitized input/output, browser context, origin, encoding/CSP behavior, reproducible steps, and realistic victim preconditions. |
| SSRF | Server fetches attacker-controlled URL; internal/cloud reachability or trust boundary may be exposed. | Proxy plus program-approved callback service; test a unique benign callback and redirects/DNS only as allowed. | Positive: callback proves server-side request or a safe allowlisted endpoint response is returned. False positive: browser/client callback, preview proxy, DNS-only resolution, or unrelated background fetch. | Use a researcher-controlled endpoint and no metadata/credential URLs. Stop after one callback; request owner-side validation for internal impact. | Unique token, callback timestamp/source evidence, request parameter, redirect behavior, no internal data, and limits. |
| File inclusion, path traversal, upload | User controls path, archive extraction, or upload destination/type; may expose files or execute content. | Source review, proxy, harmless known public fixture, metadata-only file checks, isolated test account. | Positive: traversal reaches a specifically authorized harmless fixture, or upload crosses a documented execution/access boundary. False positive: normalized path, static error, client-only filename change, or expected public download. | Use benign marker file in a researcher-owned workspace; never retrieve system secrets or upload executable payloads to production. | Sanitized path/metadata, ownership, response headers, storage/serving behavior, access control, and exact safe impact. |
| CSRF and CORS | State-changing operation lacks anti-CSRF binding, or CORS trusts an untrusted origin with credentials; may enable cross-origin action/data exposure. | Browser DevTools, proxy, two researcher-owned origins/accounts; inspect credentials, preflight, origin reflection, and CSRF token/session binding. | Positive: controlled browser performs an unauthorized state change or reads protected response cross-origin. False positive: no credentials, non-sensitive public response, same-site protections, blocked preflight, or harmless GET. | Use a reversible, low-impact owned setting only when program rules permit; otherwise demonstrate headers and ask for owner validation. | Origin, credential mode, preflight/actual response, token/cookie context, browser result, and user-interaction prerequisites. |
| OAuth, SSO, JWT | Redirect/state/nonce/issuer/audience/signature/key/expiry validation or account-linking boundary errors. | Proxy/manual flow review; use own test client/accounts, compare tokens and callback values without altering another user's identity. | Positive: reproducible authentication/account binding or authorization failure. False positive: expected unsigned metadata, accepted clock skew, public key confusion, or token accepted only by test endpoint. | Use provider sandbox/researcher tenant; do not forge tokens for other users or access their account. | Redacted claims (no signature/secret), issuer/audience, flow parameters, account ownership, and exact validated boundary. |
| GraphQL and API discovery | Unauthenticated or over-broad schema, resolver/object authorization gaps, batching/depth/rate controls; endpoint existence alone is not weakness. | API docs, browser/proxy, `curl`, approved GraphQL client; map operations and compare resolver access across controlled identities. | Positive: protected object/field/action is reachable contrary to policy or sensitive schema details create demonstrable risk. False positive: introspection enabled by design, schema names alone, 200 with errors, or authorized fixture. | Prefer one owned record/field and bounded query; don't issue expansive nested/batched queries without approval. | Operation, variables, caller role, selected fields, expected/actual access, rate/depth limits, and sanitized response. |
| Cache poisoning/deception and request smuggling | Cache key omits security-relevant input, or intermediaries parse message boundaries differently; may cross users or desynchronize services. | Carefully reviewed proxy/manual single-request tests; only on assets and techniques expressly allowed because shared caches/parsers are sensitive. | Positive: repeatable cross-session response contamination or demonstrable parser disagreement with controlled harmless marker. False positive: browser cache, cache-buster, origin variation, or proxy normalization. | Use researcher-controlled content/accounts and a non-sensitive marker; do not attempt queue disruption or affect other users. | Full sanitized request chain, cache headers/key dimensions, clean-session reproduction, intermediary path, and stop conditions. |
| Rate limits and race conditions | Missing per-account/action limits, non-atomic state transition, duplicate use; could enable abuse or inconsistent state. | Controlled accounts and isolated disposable objects; low request volume and approved concurrency only. | Positive: policy limit is bypassed or invariant fails repeatably under controlled conditions. False positive: async UI, eventual consistency, retries, or test harness artifact. | Use a reversible researcher-owned action and minimum concurrency; no load/stress testing. | Request counts/timing, account/object ownership, state before/after, repeatability, rate, and practical impact. |
| Business logic / information disclosure | Workflow invariant, account/tenant binding, price/quantity/entitlement, export, or error path exposes data/actions. | Manual workflow map, proxy, two owned accounts and test objects; compare allowed and disallowed transitions. | Positive: invariant or confidentiality boundary fails with reproducible controlled data. False positive: intended role, sample/demo data, stale response, or UI-only state. | Stop at minimum proof; redact immediately and notify through program process if unexpected real data appears. | Business rule, roles, controlled object, exact transition, redacted result, impact constraints, and remediation idea. |

For all classes: record what was attempted and what was not; identify the tool/version and rate where material; distinguish confirmed, likely, unverified, false positive, and not tested. A report should let the program reproduce the issue safely without providing a weaponized payload or unrelated data.
